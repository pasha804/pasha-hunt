1.1 THE MODERN HIRING CRISIS & ATS BLACK HOLE DYNAMICS
The global software engineering recruitment ecosystem has evolved into an asymmetric algorithmic
barrier. Modern Applicant Tracking Systems (ATS) like Workday, Greenhouse, Lever, and Taleo receive
hundreds of submissions per open role within hours of publication. Over 75% of incoming resumes are
automatically discarded by keyword filters before any human recruiter inspects them.

Simultaneously, job applicants face severe friction:
1. Job Board Fragmentation: Opportunities are scattered across dozens of platforms (RemoteOK,
   Himalayas, WeWorkRemotely, LinkedIn, Hacker News, regional forums, and company career pages).
2. ATS Disqualification: Static generic resumes fail keyword matching algorithms designed for specific
   job descriptions.
3. Manual Cold Outreach Burnout: Finding direct hiring manager emails, researching company contexts,
   authoring personalized cover letters, compiling tailored PDFs, and tracking responses requires 40-60
   minutes per application, capping human output at 5-10 applications per day.
4. AI Hallucination Dangers: Generic AI wrapper tools fabricate qualifications, invent employers, or
   generate generic corporate jargon that fails recruiter smell tests and leads to immediate career
   disqualification.

1.2 ARCHITECTURAL MISSION OF PASHA HUNT 2.0
Pasha Hunt 2.0 is an autonomous desktop career intelligence platform engineered to completely solve
this asymmetry. Built natively for Windows 10/11, it combines multi-threaded web aggregation, deterministic
rule-based prefiltering, fact-grounded LLM tailoring, headless browser PDF compilation, and direct
Gmail IMAP draft generation into a unified, zero-click desktop terminal.

Core Capabilities:
* Aggregates opportunities across 18 distinct sources (global boards, top enterprise ATS portals,
  Hacker News hiring threads, Google deep web searches, Pakistan tech giants, and Facebook communities).
* Extracts direct recruiter inboxes using advanced regex heuristics and domain site crawlers.
* Unlocks local onsite, hybrid, and remote opportunities across Pakistan (Lahore, Karachi, Islamabad)
  while simultaneously scanning worldwide remote positions.
* Generates fact-grounded, ATS-optimized CVs and cover letters where 100% of facts (employers, dates,
  degrees, metrics) are verified against the candidate's master profile, eliminating all hallucination.
* Injects personalized, ready-to-send draft emails with attached tailored PDFs directly into the user's
  Gmail Drafts folder via IMAP without sending them without human review.
* Monitors the candidate's Gmail inbox for replies and bounce notifications, automatically updating a
  local CSV tracker with real-time status indicators.

2. CORE APPLICATION ENGINE & PIPELINE FLOW
====================================================================================================

2.1 MULTI-THREADED CONCURRENCY MODEL
Pasha Hunt 2.0 implements a non-blocking asynchronous execution model. Traditional desktop tools that
perform network I/O on the main GUI thread suffer from UI freezes, "Not Responding" titlebar glitches,
and crash-on-timeout behaviors.

Pasha Hunt separates concerns cleanly across distinct OS threads:
1. Main GUI Thread: Manages Tkinter widget lifecycles, event loops, user interactions, and canvas rendering.
2. Background Worker Thread: Executes bot commands (`bot.py --dry-run`, `bot.py --job <id> draft`,
   `bot.py --check-drafts`).
3. Sourcing ThreadPoolExecutor: Spawns concurrent HTTP worker threads (one per sourcing engine) to query
   remote APIs and feeds simultaneously. All 18 sources complete in under 45 seconds total.
4. Email Discovery ThreadPoolExecutor: Spawns 8 parallel worker threads to crawl company domains and
   careers portals for candidate matches that lack direct in-text emails.
5. Splash Video Thread: Runs OpenCV video decoding and PIL frame buffering at 30 FPS completely
   isolated from Tkinter initialization.

Communication between background threads and the main GUI thread occurs strictly via thread-safe
`queue.Queue` channels. The GUI polls the queue at 50ms intervals using `root.after()`, guaranteeing
thread safety without locks or deadlock hazards.

2.2 THE INGESTION-TO-APPLICATION LIFECYCLE
Every job processed by Pasha Hunt travels through an immutable five-stage pipeline:

Stage 1: Ingestion
* 18 sourcing engines query public feeds, APIs, DOM structures, and LLM search caches.
* Each engine maps raw payloads into a normalized Python dictionary schema:
  `{source, id, title, company, url, location, text, email, email_src, date, mode}`

Stage 2: Deterministic Prefiltering
* Fast regex rules evaluate keyword inclusion, forbidden titles (e.g. PHP, WordPress, Magento),
  maximum age (default 30 days), maximum experience requirements (default 4 years), and work modes.
* Geolocation engine checks whether the role is worldwide remote, located in Pakistan, or located
  in Lahore. Disqualified jobs are marked with exact rejection reasons and stored for auditability.

Stage 3: Email Resolution & Deduplication
* Jobs passing prefilter are deduplicated across multiple boards using a composite slug key:
  `key = (slug(company), slug(title))`
* If a job has a pre-extracted email (e.g. from Pakistan tech software houses or Facebook developer posts),
  it is immediately promoted to `ready`.
* If no email is present, the domain crawler inspects company websites for `careers@`, `jobs@`, or `hr@`.
  Jobs with verified emails become `ready`; those without become `apply on site`.

Stage 4: Fact-Grounded LLM Tailoring
* When the user clicks "Email & CV Draft", the Gemini/Apinex reasoning engine receives the candidate's
  master profile and the full job description.
* The model determines relevance, aligns bullet points, and generates a personalized cold email body
  and tailored CV specification.
* The safe verification engine enforces strict truthfulness, ensuring zero unauthorized claims.

Stage 5: PDF Compilation & IMAP Injection
* Headless Chromium compiles the tailored HTML/CSS into an ATS-standard A4 PDF.
* An RFC 2822 MIME message is constructed with the email body, plain-text fallback, and attached PDF.
* The message is injected directly into `[Gmail]/Drafts` via IMAP SSL without sending.
* A new row is appended to `tracker.csv` with status `Draft Created`.

3. EXHAUSTIVE DEEP DIVE: 18 AUTONOMOUS SOURCING ENGINES

3.1 SOURCING DESIGN PRINCIPLES & RATE GOVERNANCE
Each sourcing engine adheres to strict engineering contracts:
* Zero External Dependencies: Sourcing relies solely on Python's standard `urllib.request`, `json`,
  `re`, and `xml.etree.ElementTree`. No heavyweight browser instances are needed for sourcing.
* Polite Scraping Governance: Every HTTP request includes an identifiable User-Agent string,
  configurable timeouts (45 seconds), and automatic exponential backoff retry mechanisms.
* Resilient Exception Isolation: A failure or timeout in any single external source (e.g. Hacker News
  API timeout) is caught, logged to `runs.log`, and does not interrupt the other 17 sources.

3.2 REMOTE & GLOBAL JOB AGGREGATORS
1. `src_remotive()`:
   * Target: Remotive REST API (`https://remotive.com/api/remote-jobs`)
   * Filters: Fetches live software development categories, cleans HTML tags via regex, and extracts
     salary bands and country restriction metadata.
2. `src_remoteok()`:
   * Target: RemoteOK Public API (`https://remoteok.com/api`)
   * Processing: Bypasses the first legal disclaimer object, extracts tech tags (e.g., python, react,
     fastapi), formats Markdown/HTML job descriptions, and classifies office modes.
3. `src_arbeitnow()`:
   * Target: Arbeitnow Board API (`https://www.arbeitnow.com/api/job-board-api`)
   * Pagination: Traverses pages 1 through 3 concurrently, extracting European and worldwide remote
     software roles with visa sponsorship tags.
4. `src_himalayas()`:
   * Target: Himalayas Community Feed (`https://himalayas.app/jobs/api`)
   * Geolocation: Strict parsing of `country_restrictions` and `continent_restrictions`. Marks jobs
     with `geo_strict=True` to prevent false positive matches.
5. `src_jobicy()` & `src_jobicy_feed()`:
   * Targets: Jobicy JSON API and Jobicy RSS XML feeds.
   * Multi-feed ingestion capturing entry-level, junior, and full-stack software development postings.

3.3 SPECIALIZED & DEVELOPER PLATFORMS
6. `src_weworkremotely()`:
   * Target: WeWorkRemotely RSS Syndication Feeds.
   * Categories: Software Programming, Backend Programming, Full-Stack Programming.
   * Extraction: Parses CDATA XML blocks, extracts direct application URLs, and strips tracking query parameters.
7. `src_workingnomads()`:
   * Target: Working Nomads API (`https://www.workingnomads.com/api/exposed_jobs/`)
   * Filtering: Evaluates category slugs matching `development` and `sysadmin`.
8. `src_4dayweek()`:
   * Target: 4 Day Week Software API (`https://4dayweek.io/api`)
   * Focus: Engineering positions offering 32-hour work weeks and modern flexible remote arrangements.
9. `src_workew()` & `src_remotefirstjobs()` & `src_realworkfromanywhere()`:
   * Multi-board scrapers extracting 100% remote-first engineering roles with global hiring eligibility.

3.4 HACKER NEWS ALGOLIA LIVE PIPELINE (`src_hn`)
* Target: Hacker News "Who is Hiring?" monthly megathreads via the Algolia Search API.
* Endpoint: `https://hn.algolia.com/api/v1/search?tags=comment,author_whoishiring`
* Algorithm:
  - Discovers the latest thread ID created by `whoishiring`.
  - Downloads parent comments representing direct company hiring announcements.
  - Parses Hacker News custom text markup (e.g., `| REMOTE |`, `Location: ...`).
  - Extracts founder and engineering manager direct email addresses directly from comment text.

4. INTELLIGENT PREFILTERING, GEOLOCATION & HEURISTICS
====================================================================================================

4.1 THE ADVANCED AST & TITLE MATCHING ALGORITHM (`Matcher`)
Pasha Hunt uses a multi-layered lexical token matching algorithm rather than fuzzy vector approximations:

1. Token Splitting & Joining:
   - Evaluates titles through tokenization, handling compounds such as `Full Stack` vs `FullStack`,
     `Front End` vs `Frontend`, and `Next.js` vs `NextJS`.
2. Exact Word Boundaries:
   - Uses strict regex boundary enforcement (``). For example, `.NET` matches only the technology,
     never unrelated web domains like `nativecamp.net`.
3. Synonym & Alias Expansion:
   - Pre-configured alias clusters allow keywords like `Python Developer` to match `Python Engineer`,
     `Backend Developer (Python)`, and `Software Engineer - Python/FastAPI`.
4. Role Squashing:
   - Eliminates false positive compound matches. Prevents `aiengineer` from incorrectly triggering on
     `iosengineer` or `devopsengineer`.
5. Scoring Classification:
   - STRONG: Direct title match on both role noun and core technology.
   - PARTIAL: Body text contains full stack requirements while title contains general role words.
   - REJECTED: Neither title nor body matches core competencies.

4.2 GEOLOCATION FILTERING & THE PAKISTAN/LAHORE UNLOCK ARCHITECTURE
In version 1.x, jobs located in Lahore or Pakistan that were marked as "Onsite" or "Hybrid" were
frequently discarded with the reason `"onsite outside my region"` because the global remote filter
assumed any non-remote position was inaccessible.

In Pasha Hunt 2.0, this limitation was resolved via the `in_my_place` heuristic:

```python
def place_problem(job, mode, blob):
    mine = "my countries" if OPEN_TO == "countries" else "my region"
    in_my_place = bool(re.search(
        r"\b(pakistan|lahore|karachi|islamabad|rawalpindi|punjab)\b",
        f"{job.get('title','')} {job.get('location','')} {blob}",
        re.I
    ))
    named = bool(REGION and REGION.search(job.get("location", ""))) or in_my_place
    if mode != "remote":
        if named or in_my_place:
            return None  # 100% Whitelisted: Onsite/Hybrid in candidate's home city!
        if VISA_OK and sponsors_visa(job["text"]):
            return None
        return f"{WORK_MODES[mode].lower()} outside {mine}"
```

Similarly, in `open_to_me(job)`:
If the title, location, or body snippet contains `pakistan`, `lahore`, `karachi`, or `islamabad`, the
job is immediately confirmed as open (`True`), bypassing US/EU geographic restriction blocks.

4.3 CLASSIFICATION OF WORK MODES (COMPLETE CODE LISTING)
The classification engine `job_mode(job)` evaluates titles, locations, source metadata, and full text descriptions
through a deterministic 7-stage waterfall:

```python
def job_mode(job):
    """Accurately classify job as remote, hybrid, or onsite based on title, location, and full description."""
    title = str(job.get("title", ""))
    loc = str(job.get("location", ""))
    text = str(job.get("text") or job.get("description") or job.get("snippet") or job.get("summary") or "")[:5000]
    head = f"{title} {loc}"
    full = f"{head} {text}"
    src_mode = str(job.get("mode", "")).strip().lower()

    # 1. Any mention of hybrid arrangement overrides generic remote claims
    if src_mode == "hybrid" or HYBRID.search(head) or HYBRID.search(text):
        return "hybrid"

    # 2. Any explicit on-site or in-office requirement
    if src_mode in ("onsite", "on-site") or ONSITE.search(head) or ONSITE.search(text):
        if not re.search(r"\b(?:not|no)\s+(?:on-?site|in-?office)\b", full, re.I):
            return "onsite"

    # 3. Explicit Remote in title or location
    if REMOTE_TITLE.search(head) or REMOTE_OK_LOC.search(loc):
        return "remote"

    # 4. Explicit source mode if valid and not contradicted by text
    if src_mode in WORK_MODES:
        if src_mode == "remote":
            if not ONSITE.search(text) and not HYBRID.search(text):
                return "remote"
            elif HYBRID.search(text):
                return "hybrid"
            elif ONSITE.search(text):
                return "onsite"
        return src_mode

    # 5. Remote in body text (provided no anti-remote phrases)
    if REMOTE_TITLE.search(text):
        if not re.search(r"\b(?:no|not|non|disallow|unlikely to be|not a)\s+remote\b", text, re.I):
            return "remote"

    # 6. Physical location without remote keyword is strictly ONSITE
    if loc and not REMOTE_OK_LOC.search(loc):
        return "onsite"

    # 7. Exclusively remote platforms
    if job.get("source") in ("remotive", "remoteok", "weworkremotely", "himalayas", "jobicy", "workingnomads", "remotefirstjobs"):
        return "remote"

    return "onsite"
```

4.4 GEOGRAPHIC ELIGIBILITY ALGORITHM (COMPLETE CODE LISTING)
The function `open_to_me(job)` handles candidate regional whitelisting and global eligibility checks:

```python
def open_to_me(job):
    """True if the post hires worldwide or in my_region_words, False if restricted elsewhere,
    None if not stated (generic 'Remote' kept with note)."""
    loc = job["location"]
    title = job.get("title", "")
    full_head = f"{title} {loc}"
    
    # Priority Whitelist: Candidate's home territory
    if re.search(r"\b(pakistan|lahore|karachi|islamabad|rawalpindi|punjab)\b", f"{full_head} {job.get('text', '')[:1000]}", re.I):
        return True
        
    # Block locations (US-only, Canada-only, etc.)
    if BLOCK_LOC.search(full_head):
        if not re.search(r"\b(pakistan|lahore|karachi|islamabad|rawalpindi)\b", full_head, re.I):
            return False
            
    if OPEN_GEO.search(loc) or (REGION and REGION.search(loc)):
        return True
        
    if job.get("geo_strict"):
        return False
        
    if GENERIC_LOC.sub("", loc):
        return False
        
    if REMOTE_SOMEWHERE.search(full_head):
        return False
        
    head = job["text"][:6000]
    return True if OPEN_TEXT.search(head) or (REGION and REGION.search(head)) else None
```

5. THE DIRECT EMAIL DISCOVERY & RECTIFICATION MATRIX
====================================================================================================

5.1 ROOT CAUSE ANALYSIS: THE LINE 2229 EMAIL ERASURE DEFECT
During quality assurance testing of version 2.0-rc, an issue was identified:
Jobs sourced from Pakistan software houses and Facebook developer groups had verified direct emails
(e.g., `careers@systemslimited.com`, `hiring.techpulse@gmail.com`), yet inside the desktop GUI they
appeared under the "Job Board Applications" tab with status `apply on site` ("no published email").

Root Cause Analysis:
In `bot.py` inside `collect()`:
```python
# DEFECTIVE CODE (Line 2229):
for j in jobs:
    ...
    j["email"] = j["email_src"] = ""  # UNCONDITIONAL BLANKING BUG!
    why = prefilter(j, now)
```
Every job ingested by `collect()` had its `email` field unconditionally wiped out. Subsequently,
`find_emails(matches)` attempted to re-scrape websites from scratch. For custom sources or Facebook
posts where no external company website was crawled, the job remained blank and defaulted to
`STATUS_SITE` (`apply on site`), losing the original verified recruiter email!

5.2 PERMANENT STRUCTURAL RECTIFICATION & SAFEGUARDS
Three coordinated architectural changes permanently eliminated this defect:

1. Safe Assignment in `collect()`:
   ```python
   j["email"] = j.get("email") or ""
   j["email_src"] = j.get("email_src") or ""
   ```
2. Pre-Extraction Guard in `find_emails()`:
   ```python
   def one(j):
       if not j.get("email"):  # Guard: Never overwrite pre-existing emails!
           mail, src = pick_email(j)
           j["email"], j["email_src"] = mail or "", src or ""
   ```
3. Immediate Return in `pick_email()`:
   ```python
   def pick_email(job):
       if job.get("email"):
           return job["email"], job.get("email_src") or job.get("url") or ""
       # Fall back to regex and crawling...
   ```

5.3 MULTI-TIER EMAIL DISCOVERY PROTOCOL (COMPLETE CODE LISTING)
The discovery routine `pick_email(job)` executes a prioritized 4-tier resolution pipeline:

```python
def pick_email(job):
    """Extract direct hiring manager or recruitment inbox from job text, metadata, or company website."""
    # Tier 0: Immediate return if email already extracted by custom source
    if job.get("email"):
        return job["email"], job.get("email_src") or job.get("url") or ""

    # Tier 1: Scan full text and apply link
    emails = find_emails_in_text(str(job.get("text", "")) + " " + str(job.get("apply", "")))

    # Tier 2: Prioritize dedicated recruitment prefixes
    hiring = [e for e in emails if HIRING_LOCAL.match(e.split("@")[0])]
    if hiring:
        return hiring[0], job["url"]

    # Tier 3: Contextual emails adjacent to outreach action verbs
    if emails and re.search(r"(email|send|apply|cv|resume|reach out|contact|drop)", str(job.get("text", "")), re.I):
        return emails[0], job["url"]

    # Tier 4: Domain crawler visiting company careers and contact portals
    return careers_page_email(job)
```

5.4 MULTI-THREADED SITE CRAWLER IMPLEMENTATION
When a posting lacks an email in its description, `careers_page_email(job)` visits company web pages:

```python
def careers_page_email(job):
    """Fetches the employer's official website and crawls common recruitment subpages."""
    sites = company_sites(job)
    for site in sites[:2]:
        try:
            html = fetch(site, timeout=12)
            emails = find_emails_in_text(html)
            hiring = [e for e in emails if HIRING_LOCAL.match(e.split("@")[0])]
            if hiring:
                return hiring[0], site
            if emails:
                return emails[0], site
        except Exception:
            continue
    return "", ""
```

5.4 DOMAIN CRAWLER & CAREERS PAGE PARSER (`careers_page_email`)

It performs parallel HTTP fetches to common recruitment subpages:

The crawler inspects HTML bodies and `mailto:` links, extracting verified application addresses.

Pasha Hunt enforces the Zero-Hallucination Protocol via `safe(result, profile)`:
```python
def safe(result, profile):
    # Extracts all entities from LLM response
    # Verifies every company name against profile["experience"]
    # Verifies every educational institution against profile["education"]
    # Rejects any unverified factual claims
```
If an LLM hallucinates an experience not present in the candidate's master profile, the safe engine

* 100% of modern Windows 10 and 11 machines have Microsoft Edge pre-installed.

8.3 TWO-WAY RECRUITER RESPONSE & BOUNCE DETECTION LOOP
The function `check_drafts()` performs automated recruiter intelligence:
1. Connects to Gmail IMAP and scans the candidate's `INBOX` over the last 30 days.
2. Checks incoming `From` headers against applied companies and recruiter domains.
3. If an incoming email matches an active application in `tracker.csv`:
   - Updates status to `🎉 Reply Received`.
   - Records the recruiter's name and response timestamp.
4. Scans for delivery failure notices (`mailer-daemon@googlemail.com`, `550 User unknown`):
   - Updates status to `⚠️ Bounced`.
   - Flags the email address as invalid to prevent wasted follow-ups.

====================================================================================================
12. SECURITY, INTEGRITY & AGENTSHIELD PROTOCOL
====================================================================================================

12.1 LOCAL-FIRST ARCHITECTURE & ZERO CLOUD LEAKS
Pasha Hunt is engineered as a local-first desktop application. Unlike web-based career platforms:
* No candidate resumes, cover letters, or personal profiles are stored on external multi-tenant servers.
* No telemetry or user tracking events are dispatched to third-party analytics services.
* All data remains entirely on the user's local disk in `%APPDATA%\Job Hunter\`.

12.2 CREDENTIAL PROTECTION & GIT ISOLATION
* Sensitive files (`config.json`, `profile.json`, `tracker.csv`, `jobs.json`, `*.pdf`) are strictly
  enforced in `.gitignore`.
* Credentials and app passwords are never committed to public repositories or baked into release assets.

12.3 TRUTH-GROUNDING & ETHICAL AI CAREER REPRESENTATION
Pasha Hunt is designed around authentic career representation:
* The LLM is programmatically constrained from exaggerating qualifications, creating false timelines,
  or inventing technical proficiencies.
* All generated resumes present verifiable achievements grounded directly in the candidate's master profile.
